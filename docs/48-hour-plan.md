# 48 小时模块式执行计划

## 1. 目标

ScriptForge 的 48 小时目标是做出一个可演示的 AI 辅助剧本改编工作台：输入 3 个章节以上的小说文本，选择基础改编偏好，生成带来源追踪和改编说明的结构化剧本对象，转换为 YAML，通过 Schema 与引用校验，并能在工作台中预览、轻量编辑和导出。

这份计划按模块拆分，但模块不是按技术层随意切开，而是围绕真实产品路径拆分：章节输入 → 改编意图 → AI 结构化生成 → Schema 质量控制 → 作者可读预览 → 来源追踪与改编报告 → 本地导出与演示。每个模块都必须交付这条路径上的一段可验收能力，避免最后只有 YAML 转换而看不到产品设计。

## 2. 交付边界

### 必须交付

- 小说章节输入，至少支持 3 个章节，并保留章节 ID、标题、正文和摘要。
- 内置示例文本，一键载入后可完整跑通演示。
- 基础改编偏好输入，包括目标形态、语气风格、长度或节奏倾向。
- 结构化剧本数据对象，包含来源章节、人物、地点、场景、动作/对白节拍和改编报告。
- 场景到原章节的来源追踪，关键场景能说明由哪些原文事件或心理描写改编而来。
- YAML 导出，以及导出前的 JSON Schema 校验和应用层引用校验。
- 工作台预览，包括人物、地点、场景、对白、来源章节、改编说明和校验状态。
- 轻量编辑能力，至少支持修改 YAML 或结构化输出后重新校验。
- AI 生成链路或可解释的备用生成结果，失败时不破坏演示闭环。
- README、Schema 说明文档、本地运行说明和 Demo 讲解材料。

### 可以延后

- 用户账号和云端保存。
- 多项目管理。
- 多人协作编辑。
- 复杂分镜、拍摄计划和预算管理。
- 长篇小说的完整分块处理。
- 高级结构化编辑器，例如拖拽调整场景顺序或可视化修改人物关系。

## 3. 并行开发原则

1. 先定义数据契约，再写各自模块。
2. 每个模块必须能用静态 fixture 独立运行。
3. 前端不等待 AI，先消费静态剧本对象。
4. AI 不等待完整 UI，先输出符合 Schema 的 JSON。
5. Schema 是主契约，应用层补充引用校验。
6. 每个模块都提供最小降级路径。
7. 集成关口只验收端到端路径，不做大范围重构。

## 4. 共享数据契约

所有模块围绕同一份剧本对象工作。共享契约不只描述“能转 YAML”，还要保证作者能理解 AI 做了什么、为什么这样改、后续从哪里继续打磨。

```text
NovelChapter[]
  ↓
GenerationRequest
  ├─ chapters：章节 ID、标题、正文、摘要
  └─ preferences：目标形态、语气风格、长度/节奏倾向
  ↓
ScriptForgeScript JSON
  ├─ source：输入来源与章节索引
  ├─ characters / locations：人物与地点资产
  ├─ scenes：场景、动作、对白、source_chapters
  └─ adaptation_report：保留、压缩、合并、改写和修改建议
  ↓
ValidationResult
  ├─ schema：字段结构校验
  └─ references：人物、地点、来源章节引用校验
  ↓
Workbench preview / editable YAML / export
```

### 共同对象

- `NovelChapter`：章节输入对象，包含章节 ID、章节编号、标题、正文和可选摘要；章节 ID 是后续来源追踪的稳定引用。
- `GenerationRequest`：生成请求，包含章节、目标形态、语气风格、长度或节奏偏好，以及是否优先忠于原文、强化冲突等简单开关。
- `ScriptForgeScript`：剧本结构化对象，对应 `schema/scriptforge.schema.json`；必须包含来源信息、人物、地点、场景、对白/动作节拍和改编报告。
- `SourceRef`：来源追踪引用，至少能从场景定位到原章节；关键场景可以补充来源摘要或改编依据。
- `AdaptationReport`：改编说明对象，解释保留内容、压缩内容、合并内容、改写原因和后续修改建议。
- `ValidationResult`：校验结果，包含是否通过、Schema 错误路径、引用错误和可读说明。
- `ExportPayload`：导出对象，包含 YAML、Markdown、JSON 等格式；导出前必须绑定最近一次校验状态。

### 建议文件边界

```text
src/types/scriptforge.ts         共享 TypeScript 类型
src/lib/schema.ts                Schema 加载与 Ajv 校验
src/lib/yaml.ts                  JSON/YAML 转换
src/lib/fixtures.ts              示例输入和示例输出
src/lib/ai/client.ts             AI 客户端适配
src/lib/ai/prompts.ts            Prompt 模板
src/app/api/generate/route.ts    生成 API
src/app/api/validate/route.ts    校验 API
src/app/api/repair/route.ts      修复 API
src/app/page.tsx                 工作台入口
schema/scriptforge.schema.json   JSON Schema
```

## 5. 模块拆分

### M0 项目骨架模块

负责人：前端或全栈。

目标：提供所有人可以共同开发和运行的项目基础。

输入：无。

输出：可运行的 Next.js 项目、基础目录结构、基础样式和组件约定。

主要任务：

- 初始化 Next.js、TypeScript、Tailwind CSS。
- 建立 `src/types`、`src/lib`、`src/app/api`、`schema`、`docs` 目录。
- 建立基础页面和工作台布局。
- 配置 lint、format 和基础脚本。

依赖：无。

验收：

- `pnpm dev` 或等效命令可以启动。
- 首页可以打开。
- 目录结构与模块边界一致。

降级：

- 如果 UI 组件库安装耗时，先用原生 HTML + Tailwind 完成布局。

### M1 输入、改编偏好与样例数据模块

负责人：前端或数据整理。

目标：让系统在没有 AI 的情况下也能呈现完整的“小说章节 → 改编意图 → 剧本资产”产品路径。

输入：3 个以上章节的小说文本，以及基础改编偏好。

输出：`NovelChapter[]`、`GenerationRequest` 示例、可校验的示例生成结果 `ScriptForgeScript`。

主要任务：

- 定义章节输入格式，保留章节 ID、标题、正文和可选摘要。
- 准备 3 个中等长度原创章节示例，内容要有明确人物、地点、冲突和可改编事件。
- 定义最小改编偏好，例如目标形态、语气风格、长度/节奏倾向和忠实度倾向。
- 准备一个完整的示例剧本 JSON，必须包含来源章节、人物、地点、场景、动作/对白节拍和改编报告。
- 提供一键载入示例的 fixture，载入后同时填充章节、偏好和示例输出。
- 处理空输入、章节不足、标题缺失、偏好缺省等基础情况。

依赖：M4 需要读取输入契约，M6 需要使用示例数据，M7 需要使用来源追踪和改编报告。

验收：

- 一键载入后至少有 3 个章节，并能看到章节标题和输入状态。
- 示例请求包含基础改编偏好，不需要写代码即可理解目标改编方向。
- 示例剧本 JSON 能被 M2 校验通过。
- 示例场景能回指来源章节，改编报告能解释至少 3 个改编决策。
- 示例数据能支撑完整 Demo，包括预览、校验、编辑后重校验和导出。

降级：

- 如果真实样本文本版权或长度不合适，使用原创短篇片段。
- 如果偏好项来不及做成表单，使用固定默认偏好并在工作台显示。

### M2 Schema、来源引用与校验模块

负责人：后端、全栈或数据结构设计。

目标：把题目要求的 YAML Schema 变成产品质量控制能力，确保输出不仅字段完整，而且人物、地点、场景和来源章节之间可以相互引用、可解释。

输入：`ScriptForgeScript` JSON、章节 ID 列表、可选的 YAML 编辑结果。

输出：`ValidationResult`，包含 Schema 结果、引用校验结果和面向用户的错误说明。

主要任务：

- 维护 `schema/scriptforge.schema.json`，核心字段覆盖来源、人物、地点、场景、动作/对白节拍和改编报告。
- 用 Ajv 实现 Schema 校验，输出可读的错误路径和错误说明。
- 实现应用层引用校验：场景引用的人物必须存在，地点必须存在，`source_chapters` 必须能对应到输入章节。
- 校验改编报告的最小完整度，例如保留内容、压缩内容、修改建议至少能解释主要改编变化。
- 支持 YAML 编辑后重新解析并校验，给 M6 展示错误位置和修复入口。
- 提供有效 fixture、缺字段 fixture、引用错误 fixture，便于各模块独立自测。

依赖：M1 提供示例章节和示例剧本，M3 和 M6 消费校验结果，M7 展示来源引用和报告。

验收：

- 示例剧本 JSON 校验通过。
- 删除必填字段后校验失败，并能定位到字段路径。
- 把场景地点、人物或来源章节改成不存在的 ID 时，引用校验失败。
- 校验结果能被工作台展示为通过、警告或错误状态。
- 导出模块只能使用最近一次通过校验的对象。

降级：

- 如果跨引用校验来不及，至少保留 `source_chapters` 字段和 JSON Schema 校验，并在文档说明引用校验是应用层扩展。

### M3 YAML 转换、编辑与导出模块

负责人：前端或全栈。

目标：把结构化剧本对象转换为题目要求的 YAML，同时让 YAML 成为作者可继续打磨的交付物，而不是只用于展示的中间文本。

输入：最近一次通过校验的 `ScriptForgeScript` JSON，以及可选的 YAML 编辑文本。

输出：YAML 文本、Markdown 文本、JSON 文本、下载文件、编辑后重校验结果。

主要任务：

- 实现 JSON 到 YAML 转换，并保持字段顺序稳定：来源、人物、地点、场景、改编报告。
- 导出的 YAML 必须保留 `source_chapters`、人物/地点引用和改编报告，方便作者回看来源。
- 实现 YAML 下载，并在文件名中体现项目名或生成时间。
- 支持 YAML 文本复制；最小编辑能力是用户改 YAML 后可以重新解析并调用 M2 校验。
- 可选实现 Markdown 剧本导出，用于评审快速阅读对白和场景。
- 在导出前调用 M2 校验；校验失败时阻止导出或明确提示导出的是未通过版本。

依赖：M2 校验结果，M6 导出按钮和编辑区，M7 预览字段顺序。

验收：

- 示例剧本可以导出 YAML。
- 导出的 YAML 字段完整、顺序稳定、可读，并保留来源追踪和改编报告。
- 修改 YAML 后可以重新校验，错误能回到 M2 的字段路径。
- 校验失败时能阻止或提示导出。
- 不查看代码，只打开导出 YAML，也能理解人物、地点、场景和改编依据。

降级：

- 如果 Markdown 导出做不完，保留 YAML 和 JSON。
- 如果 YAML 编辑器做不完，保留 `<textarea>` 编辑和重新校验按钮。

### M4 AI 改编生成管线模块

负责人：AI、后端或全栈。

目标：把小说章节和改编偏好转换为符合 Schema 的剧本资产 JSON，并在生成结果中保留“原文依据”和“改编决策”。

输入：`GenerationRequest`，包含章节、章节摘要和基础改编偏好。

输出：`ScriptForgeScript` JSON 或错误对象；错误对象必须说明是网络、解析、校验还是引用问题。

主要任务：

- 实现 OpenAI-compatible AI client。
- 编写 Analyzer prompt：抽取人物、地点、事件、冲突、关键心理描写和章节摘要。
- 编写 Planner prompt：根据改编偏好规划场景顺序、节奏、冲突强化点和压缩策略。
- 编写 Screenwriter prompt：生成结构化剧本对象，包括场景、动作、对白、人物/地点引用和 `source_chapters`。
- 编写 Adaptation Reporter prompt：输出保留、压缩、合并、改写和修改建议，解释小说到剧本的变化。
- 要求模型输出 JSON，不直接输出 YAML；程序负责校验、修复和转换。
- 解析模型结果后先交给 M2 校验，再交给 M3/M6/M7 使用。

依赖：M1 输入契约与偏好，M2 Schema 与引用校验，M5 修复模块。

验收：

- 输入示例章节和偏好后能返回剧本 JSON。
- 结果包含人物、地点、场景、动作/对白节拍、来源章节和改编报告。
- 每个场景至少引用一个来源章节。
- 结果可以转 YAML，并在一次修复以内通过 Schema 与引用校验。
- 生成失败时能返回结构化错误，工作台不会空白。

降级：

- 如果 AI 调用失败，返回 M1 的内置示例输出，并在界面显示降级状态。
- 如果多阶段 prompt 耗时过长，合并为一次 prompt，但输出字段仍必须满足 Schema、来源追踪和改编报告要求。

### M5 自动修复与容错模块

负责人：后端或 AI。

目标：降低模型格式错误、引用错误、网络失败和现场演示失败的概率，让质量控制不是“报错即结束”，而是能帮助作者回到可编辑闭环。

输入：模型输出、`ValidationResult`、原始章节、改编偏好、最近一次有效剧本对象。

输出：修复后的 `ScriptForgeScript`、带状态的降级结果或可读错误。

主要任务：

- 实现 `/api/repair`。
- 根据 Schema 错误生成结构修复 prompt，优先补齐字段、修正类型、保持字段顺序。
- 根据引用错误修复人物、地点和来源章节引用，不凭空创建无法解释的来源。
- 修复只处理结构、字段缺失和轻量引用问题，不重新创作故事主线。
- 统一处理 AI 超时、解析失败、Schema 失败、引用失败和 YAML 编辑失败。
- 准备内置生成结果作为最终 fallback，并标注 fallback 来源。
- 保留错误说明，供 M6 展示“为什么没通过、如何恢复”。

依赖：M2 校验，M4 生成结果，M1 示例输出，M6 状态展示。

验收：

- 删除必填字段后可以自动补齐结构或给出明确失败原因。
- 把场景引用改错后能尝试修复或提示可选有效 ID。
- 模型失败时仍能展示完整剧本闭环。
- 错误状态、修复状态和 fallback 状态在 UI 中可见且可解释。
- fallback 结果仍可预览、校验和导出。

降级：

- 如果 repair 做不完，保留“使用示例结果”的按钮，并显示当前不是实时 AI 生成结果。

### M6 作者工作台 UI 模块

负责人：前端。

目标：让评委和作者能按真实产品路径完成一次改编：载入章节、选择偏好、生成剧本、查看质量状态、理解改编依据、轻量编辑并导出。

输入：`NovelChapter[]`、改编偏好、生成状态、`ScriptForgeScript`、`ValidationResult`、导出状态。

输出：可操作的本地作者工作台页面。

主要任务：

- 实现章节输入区，显示章节数、标题完整性和基础输入状态。
- 实现一键载入示例，同时填充章节、偏好和可演示输出。
- 实现改编偏好区，至少包含目标形态、语气风格、长度/节奏倾向。
- 实现生成按钮和流程状态，例如分析章节、规划场景、生成对白、校验结构、准备预览。
- 实现校验状态展示，区分通过、警告、错误、修复中和 fallback。
- 实现 YAML 编辑区或只读展示；如果可编辑，修改后能触发重新校验。
- 实现人物表、地点表、场景卡片、对白预览、来源章节和改编说明入口。
- 实现导出按钮，只导出最近一次通过校验或明确标注状态的版本。

依赖：M1 fixture，M2 校验，M3 导出，M4 API，M5 fallback，M7 预览组件。

验收：

- 用户不看代码也能完成一次“载入 3 章 → 选择偏好 → 生成/加载结果 → 校验 → 预览 → 导出”。
- 页面能解释当前结果来自 AI、修复结果还是内置示例。
- 从左到右或从上到下能看懂输入、改编意图、生成状态、质量状态和输出。
- 修改 YAML 或结构化输出后能重新校验，并在 UI 中看到错误或通过状态。
- 生成失败和降级状态不会让页面空白。

降级：

- 如果编辑器集成耗时，先使用 `<textarea>` 或 `<pre>` 展示 YAML。
- 如果偏好表单做不完，使用固定默认偏好并展示在页面上。

### M7 剧本预览、来源追踪与改编报告模块

负责人：前端、产品或内容。

目标：让输出不只是一份 YAML，而是能被作者理解、质疑和继续修改的剧本初稿。

输入：`ScriptForgeScript`、`NovelChapter[]`、`ValidationResult`。

输出：人物摘要、地点摘要、场景列表、对白预览、来源追踪视图、改编报告。

主要任务：

- 展示角色表，包含角色功能、人物弧光和首次出现章节。
- 展示地点表，包含视觉提示和关联场景。
- 展示场景卡片，包含场景标题、地点、时间、出场人物、动作/对白节拍和来源章节。
- 展示对白和动作文本，让评委不读 YAML 也能看懂剧本。
- 展示来源追踪：每个场景至少显示来源章节，关键场景显示来源摘要或改编依据。
- 展示改编报告：保留内容、压缩内容、合并/改写内容、修改建议。
- 标出校验警告，例如缺少来源、引用不存在或报告过短。

依赖：M1 示例剧本，M2 校验结果，M6 工作台布局。

验收：

- 不查看 YAML 也能理解剧本内容。
- 每个场景能看到来源章节。
- 至少 3 条改编决策能对应到场景或章节。
- 改编报告能解释小说到剧本的变化，而不是只复述字段。
- 预览能显示校验状态，避免作者误以为无效结果可直接交付。

降级：

- 如果完整预览做不完，优先展示场景列表、对白、来源章节和改编报告。

### M8 文档、本地部署与演示模块

负责人：产品、全栈或讲解者。

目标：补齐提交材料，固定本地演示路径，并把产品创新点写进仓库访问者能理解的叙述中。

输入：项目功能、Schema、Demo 路径、改编前后示例、来源追踪和校验样例。

输出：README、Schema 说明、Demo 脚本、本地运行说明、创新点说明。

主要任务：

- 维护 README，面向仓库访问者说明产品价值，不写成内部阶段汇报。
- 维护 YAML Schema 说明文档，解释为什么需要来源、人物、地点、场景、对白和改编报告字段。
- 维护本地演示脚本，覆盖载入示例、选择偏好、生成/降级、校验、预览、编辑、导出。
- 准备 1 分钟、3 分钟、5 分钟讲解版本。
- 固化本地运行命令、环境变量说明和演示数据路径；演示范围限定为本地部署。
- 梳理产品创新点，并写入 README 与 Demo 话术。

创新点需要覆盖：

- 从聊天式文本生成升级为结构化剧本资产生成。
- 用 YAML Schema 和引用校验约束人物、地点、场景、对白、来源章节和改编报告，降低 AI 输出不可控风险。
- 保留小说章节到剧本元素的可追溯关系，让作者能判断 AI 改编是否合理。
- 把改编报告作为产品核心输出，说明保留、压缩、合并和修改建议。
- 内置校验、修复和 fallback，让 48 小时作品具备稳定本地演示能力。

依赖：M2 Schema，M6 工作台，M7 预览。

验收：

- README 面向仓库访问者可读，不使用内部汇报口吻。
- Schema 文档说明字段设计原因，尤其是来源追踪和改编报告。
- Demo 路径能在本地连续跑通 3 次。
- README 或 Demo 脚本清楚说明产品创新点，并能对应到实际界面。
- 本地运行说明清楚，演示环境可以启动。

降级：

- 如果真实 AI 调用失败，使用本地示例输出和录屏备份，但 Demo 必须明确显示降级状态。

## 6. 并行泳道

### 泳道 A：前端工作台与预览

负责模块：M0、M6、M7。

先用 fixture 做出本地作者工作台，再接真实 API。工作台必须持续呈现产品路径：章节输入、改编偏好、生成状态、质量状态、预览、来源追踪、改编报告和导出。

第一优先级：页面可打开，示例可载入，偏好可见，YAML 可展示或编辑，校验状态可见，场景预览能显示来源章节和改编说明。

### 泳道 B：数据契约与质量控制

负责模块：M1、M2、M3。

先冻结核心契约，再让其他模块围绕它开发。核心字段必须覆盖章节 ID、改编偏好、来源引用、人物/地点/场景引用、改编报告和导出校验状态。

第一优先级：示例请求和示例剧本可用，Schema 与引用校验可执行，YAML 可导出，编辑后能重新校验。

### 泳道 C：AI 改编生成与容错

负责模块：M4、M5。

先让 AI 输出符合契约的 JSON，再处理修复和 fallback。AI 结果必须能解释“从哪些章节改编而来”和“做了哪些保留、压缩、合并或改写”。

第一优先级：输入示例章节和偏好后返回可校验的剧本对象；失败时回到可解释的修复状态或示例结果。

### 泳道 D：文档与演示

负责模块：M8。

不等功能全部完成，先围绕仓库访问者和评委准备材料。文档必须把创新点绑定到实际界面和数据结构，而不是单独写概念。

第一优先级：README、Schema 设计说明、产品创新点、Demo 话术覆盖题目要求，并明确本地部署即可。

## 9. 集成规则

- 每个模块先用 fixture 自测，再接真实依赖。
- 合并前必须说明输入、输出、失败状态和降级状态。
- 不在集成关口临时改变 Schema 字段名；必须改时同步类型、fixture、校验、导出、预览和文档。
- UI 必须能处理 `idle`、`loading`、`success`、`warning`、`error`、`repairing`、`fallback` 状态。
- AI 返回结果必须先校验，再进入导出和预览。
- 导出必须使用最近一次已经校验过的对象；未通过校验的导出必须明确标注状态。
- fallback 不隐藏，界面应提示当前使用的是示例结果或修复结果。
- 来源追踪和改编报告是核心功能，不得在集成时被当作可选装饰字段删除。

## 11. 风险与降级

### 模型输出格式不稳定

优先让模型输出 JSON，程序负责转 YAML。失败时走 repair；repair 仍失败时使用内置示例结果。无论走哪条路径，最终对象都必须经过 Schema 与引用校验。

### 网络或 API 不稳定

保留本地示例输入、默认改编偏好和示例输出。Demo 时可以完整展示本地产品闭环，并明确当前是真实生成、修复结果还是示例结果。

### 长文本处理太慢

Demo 使用 3 个中等长度章节。生产方向可以扩展为分块摘要、增量生成和章节缓存，但 48 小时版本必须保留章节 ID，避免来源追踪断裂。

### 来源追踪不够细

最低要求是每个场景引用来源章节。来不及时不做句级引用，但关键场景要有来源摘要或改编依据。

### UI 做不完

保留核心工作台路径：章节输入、改编偏好、生成按钮、校验状态、YAML、场景预览、来源章节、改编报告和导出。其他视觉优化后置。

### Schema 过复杂

保留核心字段，引用关系放到应用层校验。不要让模型输出过深嵌套，但不能删除来源追踪和改编报告。

### 团队协作冲突

每个模块只改自己的文件边界。共享类型和 Schema 的修改必须在时间关口前同步，并同步 fixture、校验、导出、预览和文档。
