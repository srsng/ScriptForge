# 48 小时执行计划

## 1. 执行原则

ScriptForge 的 48 小时目标不是做一个功能堆满的完整平台，而是做出一个稳定、清晰、能打动评委的端到端 Demo。

优先级顺序：

1. 完整闭环优先于功能数量。
2. Schema 校验优先于文本华丽度。
3. 可演示稳定性优先于真实长文本极限能力。
4. 先用样例数据跑通，再接入真实 AI。
5. 每个阶段都保留降级方案，避免现场网络或模型波动导致 Demo 失败。

## 2. 最小可获胜版本

最小可获胜版本必须做到：

- 有一个可用工作台界面。
- 可以输入或载入至少 3 个章节。
- 可以生成结构化剧本对象。
- 可以转换为 YAML。
- 可以通过 Schema 校验。
- 可以展示人物、地点、场景、对白和改编报告。
- 可以导出 YAML。
- 有一份 Schema 文档说明设计原因。

只要这条链路稳定，项目就具备答辩竞争力。

## 3. 时间切分

### 第 0-4 小时：项目骨架和静态闭环

目标：让项目可以运行，并用静态数据展示完整界面。

任务：

- 初始化 Next.js + TypeScript 项目。
- 配置 Tailwind CSS 和基础 UI 组件。
- 建立主工作台布局。
- 准备 3 章小说样例。
- 准备一份静态剧本 JSON 样例。
- 实现 YAML 展示和预览区。

验收：

- 打开页面即可看到工作台。
- 点击“载入示例”可以填充 3 章小说。
- 页面能展示静态生成结果。

### 第 4-10 小时：Schema 与导出

目标：先把结构化资产跑通。

任务：

- 完成 `schema/scriptforge.schema.json`。
- 使用 Ajv 实现 Schema 校验。
- 实现应用层引用校验。
- 实现 JSON 到 YAML 的转换。
- 实现 YAML 和 Markdown 导出。

验收：

- 静态样例能通过校验。
- 人为删除必填字段后能看到错误。
- YAML 文件可以导出。

### 第 10-18 小时：AI 生成 API

目标：接入真实模型生成链路。

任务：

- 实现 AI client。
- 实现 `/api/generate`。
- 编写 Analyzer、Planner、Screenwriter prompts。
- 要求模型输出 JSON。
- 对模型输出做解析、校验和错误处理。

验收：

- 输入示例章节后，AI 能生成剧本 JSON。
- 生成结果可以转为 YAML。
- 生成结果至少在一次修复后能通过 Schema 校验。

### 第 18-26 小时：自动修复和容错

目标：降低 Demo 翻车概率。

任务：

- 实现 `/api/validate`。
- 实现 `/api/repair`。
- 校验失败时展示错误路径。
- 自动修复只修改结构问题，不重新创作故事。
- 准备内置 demo 输出作为网络失败降级方案。

验收：

- 删除字段后可自动修复。
- AI 调用失败时仍可展示内置结果。
- 校验错误信息可读。

### 第 26-34 小时：工作台 UI 打磨

目标：让评委一眼看懂产品价值。

任务：

- 优化三栏布局。
- 增加流程状态指示。
- 增加人物表、地点表、场景卡片。
- 增加剧本文本预览。
- 增加改编报告区。
- 增加风格选择：短剧、电影剧本、舞台剧。

验收：

- 从左到右能看懂输入、分析、输出。
- 不看 YAML 也能理解剧本内容。
- YAML 校验状态清晰。

### 第 34-40 小时：文档和答辩材料

目标：补齐题目明确要求和路演材料。

任务：

- 完成 YAML Schema 文档。
- 完成项目 README。
- 准备 Demo 讲解稿。
- 准备 1 分钟、3 分钟、5 分钟三个版本讲法。
- 准备评委可能问题和回答。

验收：

- 文档能解释 Schema 设计原因。
- Demo 脚本清楚覆盖题目要求。

### 第 40-46 小时：测试和部署

目标：保证现场可用。

任务：

- 测试示例输入。
- 测试空输入、少于 3 章、超长章节。
- 测试模型失败降级。
- 测试导出文件。
- 部署到可访问环境。
- 准备本地运行备份。

验收：

- Demo 路径连续跑 3 次不失败。
- 断网或 API 失败时仍能演示静态闭环。

### 第 46-48 小时：最终彩排

目标：压缩表达，控制节奏。

任务：

- 按正式时长彩排。
- 减少不必要点击。
- 准备开场话术和收尾话术。
- 检查浏览器、网络、环境变量和示例文件。

验收：

- 讲解者能在限定时间内完整展示。
- 备用方案明确。

## 4. 团队分工建议

如果有 2 人：

- A：前端工作台、预览、导出、演示体验。
- B：AI 管线、Schema 校验、修复、文档。

如果有 3 人：

- A：前端工作台与交互。
- B：AI 管线与 Prompt。
- C：Schema、校验、样例数据、答辩材料。

如果只有 1 人：

- 先做静态闭环。
- 再做 Schema 校验。
- 再接 AI。
- 最后做 UI 打磨。

## 5. 风险与降级方案

### 风险：模型输出格式不稳定

降级：模型输出 JSON，程序转 YAML；失败时调用 repair；仍失败时使用内置示例输出。

### 风险：现场网络不稳定

降级：准备本地示例数据和静态生成结果，至少完整展示产品闭环。

### 风险：长文本处理太慢

降级：Demo 使用 3 个中等长度章节；说明生产版会支持分块摘要和增量生成。

### 风险：UI 打磨不完

降级：优先保留章节输入、生成按钮、YAML、校验、预览五个关键区块。

### 风险：Schema 太复杂导致生成失败

降级：保留核心字段，应用层再补充引用校验；不要让模型输出过深嵌套。

## 6. 每日里程碑

### 第一天结束前必须完成

- 项目可运行。
- 工作台静态界面完成。
- 示例数据完成。
- Schema 文件完成。
- 静态 JSON 能转 YAML 并通过校验。

### 第二天中午前必须完成

- AI 生成 API 能跑。
- 自动修复能跑。
- 预览和导出能跑。

### 提交前必须完成

- Demo 路径彩排。
- Schema 文档完成。
- README 完成。
- 部署或本地演示环境稳定。

## 7. 验收清单

- [ ] 至少 3 个章节输入。
- [ ] 一键载入示例。
- [ ] 一键生成剧本。
- [ ] 输出 YAML。
- [ ] Schema 校验通过。
- [ ] 校验失败能展示错误。
- [ ] 场景包含来源章节。
- [ ] 剧本预览可读。
- [ ] YAML 可导出。
- [ ] Schema 文档说明设计原因。
- [ ] Demo 备用数据可用。
