# 48 小时模块式执行计划

## 1. 目标

ScriptForge 的 48 小时目标是做出一个稳定的端到端闭环：输入 3 个章节以上的小说文本，生成结构化剧本对象，转换为 YAML，通过 Schema 校验，并能预览和导出。

这份计划按模块拆分，目的是让多人可以并行开发。每个模块都有清晰的输入、输出、依赖、验收标准和降级方案，避免所有工作都卡在同一条时间线上。

## 2. 交付边界

### 必须交付

- 小说章节输入，至少支持 3 个章节。
- 内置示例文本，一键载入。
- 结构化剧本数据对象。
- YAML 导出。
- JSON Schema 校验。
- 剧本预览，包括人物、地点、场景、对白和改编报告。
- AI 生成链路或可解释的备用生成结果。
- README、Schema 说明文档、Demo 讲解材料。

### 可以延后

- 用户账号和云端保存。
- 多项目管理。
- 多人协作编辑。
- 复杂分镜、拍摄计划和预算管理。
- 长篇小说的完整分块处理。
- 细粒度版本历史。

## 3. 并行开发原则

1. 先定义数据契约，再写各自模块。
2. 每个模块必须能用静态 fixture 独立运行。
3. 前端不等待 AI，先消费静态剧本对象。
4. AI 不等待完整 UI，先输出符合 Schema 的 JSON。
5. Schema 是主契约，应用层补充引用校验。
6. 每个模块都提供最小降级路径。
7. 集成关口只验收端到端路径，不做大范围重构。

## 4. 共享数据契约

所有模块围绕同一份剧本对象工作。

```text
NovelChapter[]
  ↓
GenerationRequest
  ↓
ScriptForgeScript JSON
  ↓
YAML text
  ↓
Schema validation result
  ↓
Workbench preview / export
```

### 共同对象

- `NovelChapter`：章节输入对象，包含章节编号、标题和正文。
- `GenerationRequest`：生成请求，包含章节、目标格式、风格和长度偏好。
- `ScriptForgeScript`：剧本结构化对象，对应 `schema/scriptforge.schema.json`。
- `ValidationResult`：校验结果，包含是否通过、错误路径、错误说明。
- `ExportPayload`：导出对象，包含 YAML、Markdown、JSON 等格式。

### 建议文件边界

```text
src/types/scriptforge.ts         共享 TypeScript 类型
src/lib/schema.ts                Schema 加载与 Ajv 校验
src/lib/yaml.ts                  JSON/YAML 转换
src/lib/fixtures.ts              示例输入和示例输出
src/lib/ai/client.ts             AI 客户端适配
src/lib/ai/prompts.ts            Prompt 模板
src/app/api/generate/route.ts    生成 API
src/app/api/validate/route.ts    校验 API
src/app/api/repair/route.ts      修复 API
src/app/page.tsx                 工作台入口
schema/scriptforge.schema.json   JSON Schema
```

## 5. 模块拆分

### M0 项目骨架模块

负责人：前端或全栈。

目标：提供所有人可以共同开发和运行的项目基础。

输入：无。

输出：可运行的 Next.js 项目、基础目录结构、基础样式和组件约定。

主要任务：

- 初始化 Next.js、TypeScript、Tailwind CSS。
- 建立 `src/types`、`src/lib`、`src/app/api`、`schema`、`docs` 目录。
- 建立基础页面和工作台布局。
- 配置 lint、format 和基础脚本。

依赖：无。

验收：

- `pnpm dev` 或等效命令可以启动。
- 首页可以打开。
- 目录结构与模块边界一致。

降级：

- 如果 UI 组件库安装耗时，先用原生 HTML + Tailwind 完成布局。

### M1 输入与样例数据模块

负责人：前端或数据整理。

目标：让系统在没有 AI 的情况下也有稳定输入和演示数据。

输入：3 个以上章节的小说文本。

输出：`NovelChapter[]`、示例生成结果 `ScriptForgeScript`。

主要任务：

- 定义章节输入格式。
- 准备 3 个中等长度章节示例。
- 准备一个完整的示例剧本 JSON。
- 提供一键载入示例的 fixture。
- 处理空输入、章节不足、标题缺失等基础情况。

依赖：M4 需要读取输入契约，M6 需要使用示例数据。

验收：

- 一键载入后至少有 3 个章节。
- 示例剧本 JSON 能被 M2 校验通过。
- 示例数据能支撑完整 Demo。

降级：

- 如果真实样本文本版权或长度不合适，使用原创短篇片段。

### M2 Schema 与校验模块

负责人：后端、全栈或数据结构设计。

目标：把题目要求的 YAML Schema 变成可执行校验能力。

输入：`ScriptForgeScript` JSON。

输出：`ValidationResult`。

主要任务：

- 维护 `schema/scriptforge.schema.json`。
- 用 Ajv 实现 Schema 校验。
- 输出可读的错误路径和错误说明。
- 实现应用层引用校验，例如场景引用人物、地点、来源章节。
- 提供校验工具函数给 API 和前端使用。

依赖：M1 提供示例剧本，M3 和 M6 消费校验结果。

验收：

- 示例剧本 JSON 校验通过。
- 删除必填字段后校验失败。
- 校验错误能定位到字段路径。

降级：

- 如果跨引用校验来不及，先完成 JSON Schema 校验，并在文档说明应用层扩展校验。

### M3 YAML 转换与导出模块

负责人：前端或全栈。

目标：把结构化剧本对象转换为题目要求的 YAML，并支持导出。

输入：`ScriptForgeScript` JSON。

输出：YAML 文本、Markdown 文本、JSON 文本、下载文件。

主要任务：

- 实现 JSON 到 YAML 转换。
- 保持字段顺序稳定，便于评审阅读。
- 实现 YAML 下载。
- 可选实现 Markdown 剧本导出。
- 在导出前调用 M2 校验。

依赖：M2 校验结果，M6 导出按钮。

验收：

- 示例剧本可以导出 YAML。
- 导出的 YAML 字段完整、可读。
- 校验失败时能阻止或提示导出。

降级：

- 如果 Markdown 导出做不完，保留 YAML 和 JSON。

### M4 AI 生成管线模块

负责人：AI、后端或全栈。

目标：把小说章节转换为符合 Schema 的结构化剧本 JSON。

输入：`GenerationRequest`。

输出：`ScriptForgeScript` JSON 或错误对象。

主要任务：

- 实现 OpenAI-compatible AI client。
- 编写 Analyzer prompt：抽取人物、地点、事件、冲突。
- 编写 Planner prompt：规划场景和节奏。
- 编写 Screenwriter prompt：生成剧本结构。
- 要求模型输出 JSON，不直接输出 YAML。
- 解析模型结果，并交给 M2 校验。

依赖：M1 输入契约，M2 Schema，M5 修复模块。

验收：

- 输入示例章节后能返回剧本 JSON。
- 结果可以转 YAML。
- 结果至少在一次修复后通过 Schema 校验。

降级：

- 如果 AI 调用失败，返回 M1 的内置示例输出，并在界面显示降级状态。

### M5 自动修复与容错模块

负责人：后端或 AI。

目标：降低模型格式错误、网络失败和现场演示失败的概率。

输入：模型输出、`ValidationResult`、原始章节。

输出：修复后的 `ScriptForgeScript` 或降级结果。

主要任务：

- 实现 `/api/repair`。
- 根据校验错误生成结构修复 prompt。
- 修复只处理结构和字段缺失，不重新创作故事。
- 统一处理 AI 超时、解析失败、Schema 失败。
- 准备内置生成结果作为最终 fallback。

依赖：M2 校验，M4 生成结果，M1 示例输出。

验收：

- 删除必填字段后可以自动补齐结构。
- 模型失败时仍能展示完整剧本闭环。
- 错误状态在 UI 中可见且可解释。

降级：

- 如果 repair 做不完，保留“使用示例结果”的按钮。

### M6 工作台 UI 模块

负责人：前端。

目标：让评委和使用者能直观看到输入、生成、校验、预览、导出的完整流程。

输入：`NovelChapter[]`、生成状态、`ScriptForgeScript`、`ValidationResult`。

输出：可操作的工作台页面。

主要任务：

- 实现章节输入区。
- 实现一键载入示例。
- 实现生成按钮和流程状态。
- 实现 YAML 编辑器或只读展示。
- 实现校验状态展示。
- 实现人物表、地点表、场景卡片和剧本文本预览。
- 实现导出按钮。

依赖：M1 fixture，M2 校验，M3 导出，M4 API。

验收：

- 用户不看代码也能完成一次生成。
- 从左到右能看懂输入、分析、输出。
- 生成失败和降级状态不会让页面空白。

降级：

- 如果编辑器集成耗时，先使用 `<textarea>` 或 `<pre>` 展示 YAML。

### M7 剧本预览与改编报告模块

负责人：前端、产品或内容。

目标：让输出不只是一份 YAML，而是能被作者理解和继续修改的剧本初稿。

输入：`ScriptForgeScript`。

输出：人物摘要、地点摘要、场景列表、对白预览、改编报告。

主要任务：

- 展示角色表。
- 展示地点表。
- 展示场景卡片。
- 展示对白和动作文本。
- 展示改编报告：保留内容、压缩内容、修改建议。
- 标出场景来源章节。

依赖：M1 示例剧本，M6 工作台布局。

验收：

- 不查看 YAML 也能理解剧本内容。
- 每个场景能看到来源章节。
- 改编报告能解释小说到剧本的变化。

降级：

- 如果完整预览做不完，优先展示场景列表和对白。

### M8 文档、本地部署与演示模块

负责人：产品、全栈或讲解者。

目标：补齐提交材料，固定本地演示路径，并讲清产品创新点。

输入：项目功能、Schema、Demo 路径、改编前后示例。

输出：README、Schema 说明、Demo 脚本、本地运行说明、创新点说明。

主要任务：

- 维护 README。
- 维护 YAML Schema 说明文档。
- 维护演示脚本。
- 准备 1 分钟、3 分钟、5 分钟讲解版本。
- 固化本地运行命令、环境变量说明和演示数据路径。
- 梳理产品创新点，并写入 README 与 Demo 话术。

创新点需要覆盖：

- 从聊天式文本生成升级为结构化剧本资产生成。
- 用 YAML Schema 约束人物、地点、场景、对白和改编报告，降低 AI 输出不可控风险。
- 保留小说章节到剧本元素的可追溯关系，方便作者继续修改。
- 内置校验、修复和 fallback，让 48 小时作品具备稳定演示能力。

依赖：M2 Schema，M6 工作台，M7 预览。

验收：

- README 面向仓库访问者可读。
- Schema 文档说明字段设计原因。
- Demo 路径能在本地连续跑通 3 次。
- README 或 Demo 脚本清楚说明产品创新点。

降级：

- 如果真实 AI 调用失败，使用本地示例输出和录屏备份。

## 6. 并行泳道

### 泳道 A：前端工作台

负责模块：M0、M6、M7。

先做静态闭环，再接真实 API。

第一优先级：页面可打开、示例可载入、YAML 和预览可展示。

### 泳道 B：数据契约与导出

负责模块：M1、M2、M3。

先冻结核心 Schema，再让其他模块围绕它开发。

第一优先级：示例剧本通过校验，YAML 可以导出。

### 泳道 C：AI 生成与修复

负责模块：M4、M5。

先让 AI 输出 JSON，再处理修复和 fallback。

第一优先级：输入示例章节后返回可校验的剧本对象。

### 泳道 D：文档与演示

负责模块：M8。

不等功能全部完成，先围绕题目要求准备说明材料。

第一优先级：README、Schema 设计说明、产品创新点、Demo 话术覆盖题目要求。

## 8. 时间关口

### T+4 小时：骨架关口

必须完成：

- 项目可以运行。
- 工作台页面可以打开。
- `NovelChapter` 和 `ScriptForgeScript` 类型有初版。
- 示例章节和示例剧本对象有初版。

允许未完成：

- AI 调用。
- 自动修复。
- 本地演示链路。

### T+10 小时：契约关口

必须完成：

- Schema 初版冻结。
- 示例剧本通过 Schema 校验。
- JSON 可以转 YAML。
- 前端可以展示静态 YAML 和静态预览。

允许未完成：

- 真实 AI 生成。
- Markdown 导出。
- UI 精修。

### T+18 小时：生成关口

必须完成：

- `/api/generate` 可以返回剧本 JSON。
- AI 输出失败时能使用示例结果。
- 前端可以触发生成流程。

允许未完成：

- repair 的高质量结果。
- 完整错误解释。
- 本地演示链路。

### T+28 小时：闭环关口

必须完成：

- 输入、生成、校验、预览、导出全链路跑通。
- 校验失败能展示错误。
- fallback 可用。

允许未完成：

- 复杂动画。
- 高级编辑能力。
- 多种剧本格式。

### T+38 小时：演示关口

必须完成：

- Demo 路径连续跑通 2 次。
- README 和 Schema 文档可读。
- README 或 Demo 脚本说明产品创新点。
- 演示脚本覆盖题目要求。
- 本地运行说明可用，演示环境可以启动。

允许未完成：

- 非关键样式优化。
- 额外导出格式。

### T+46 小时：冻结关口

必须完成：

- 不再改核心数据结构。
- 只修复阻断 Demo 的问题。
- Demo 路径连续跑通 3 次。
- 讲解者完成正式彩排。

## 9. 集成规则

- 每个模块先用 fixture 自测，再接真实依赖。
- 合并前必须说明输入、输出和失败状态。
- 不在集成关口临时改变 Schema 字段名。
- UI 必须能处理 `loading`、`success`、`error`、`fallback` 四种状态。
- AI 返回结果必须先校验，再进入导出和预览。
- 导出必须使用已经校验过的对象。
- fallback 不隐藏，界面应提示当前使用的是示例结果或修复结果。

## 11. 风险与降级

### 模型输出格式不稳定

优先让模型输出 JSON，程序负责转 YAML。失败时走 repair；repair 仍失败时使用内置示例结果。

### 网络或 API 不稳定

保留本地示例输入和示例输出。Demo 时可以完整展示静态闭环，并说明真实生成链路的接入位置。

### 长文本处理太慢

Demo 使用 3 个中等长度章节。生产方向可以扩展为分块摘要、增量生成和章节缓存。

### UI 做不完

保留五个关键区块：章节输入、生成按钮、YAML、校验、预览。其他内容后置。

### Schema 过复杂

保留核心字段，引用关系放到应用层校验。不要让模型输出过深嵌套。

### 团队协作冲突

每个模块只改自己的文件边界。共享类型和 Schema 的修改必须在时间关口前同步。
